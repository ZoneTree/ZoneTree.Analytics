# ZoneTree Analytics dashboard

A static, multi-page dashboard generated by **PureStack**, with independent **RegorApp** mounts. It connects directly to the read-only reporting API in `ZoneTree.Analytics.AspNetCore`.

## Run locally

Requires Node.js 22.17 or newer and Corepack-enabled Yarn. The repository root pins Yarn and owns the lockfile for both the dashboard and docs site. From the repository root:

```sh
yarn install
yarn dashboard:dev
```

Open **http://127.0.0.1:4500/**. PureStack's development middleware serves demo settings from `GET /_analytics/api/config` and acts as a signed-in administrator. Date ranges, comparisons, filters, breakdowns, and CSV exports work in demo mode. Advanced query expressions and ordered funnel evaluation require the live API.

Sign-in, setup, account and administration pages need the .NET server; in the standalone preview they explain that instead of loading.

## Run with the real .NET engine

From the repository root, install dependencies once:

```sh
yarn install
```

From the repository root:

```sh
yarn dashboard --Analytics:SeedDemo=true
```

Open **http://127.0.0.1:5088/**. This .NET 10 application serves the static dashboard and reporting API on the same origin, and supplies live connection settings through `GET /_analytics/api/config`. A fresh server opens the setup wizard: open the setup link printed at the end of the console output (or enter its key), create the administrator, and choose sites, time zone and collection. The optional flag then records synthetic traffic through the real engine on an empty primary site; it never erases existing data. To read a compatible existing store, choose its directory under **Advanced settings** during setup. A data directory can only be opened by one engine at a time.

The `dotnet run` launch profile uses **Development** mode. The host starts PureStack's native development server automatically and serves its generated pages through port 5088. Editing MDX, page TypeScript, shared components, styles, or configuration rebuilds the affected pages and reloads the browser. Reporting and tracker requests still use the real .NET endpoints. No separate `yarn dev` or manual publish is needed. Stopping the host stops its PureStack child process.

Set `--Dashboard:Watch=false` to serve an existing static release in Development. Override the source directory with `--Dashboard:SourcePath=<dashboard directory>` or the Node executable with `--Dashboard:NodePath=<node executable>`.

In **Production**, run `yarn publish` first. The server serves `apps/ZoneTree.Analytics.Dashboard/ui/dist/publish`; override it with `--Dashboard:Path=<absolute path>`. The application binds to all network interfaces by default. Every page and report requires signing in; serve it over HTTPS outside a trusted network.

Every dashboard page loads the host's `/_analytics/script.js` tracker with localhost tracking enabled and `data-track-navigation="false"`. It records the page load without counting report-filter and date changes through `history.replaceState` as extra visits. Dashboard visits are recorded in the administrator-only **Dashboard usage** site when **Record dashboard usage** is on in **Administration → Sites**, and ignored otherwise. Page views increase on visits; unique visitors count distinct visitors. Refresh reports to see ingested traffic, or wait for the configured auto-refresh interval. Standalone PureStack previews keep synthetic demo reports and acknowledge beacons without persisting them.

The primary engine is configured in **Administration**: setup chooses the first settings, and
the admin pages change them, reopening the engine when needed. The Development datasets are
configured in `apps/ZoneTree.Analytics.Dashboard/server/DashboardAnalyticsOptions.cs`:
`ConfigureCommon` holds retention, storage, ingestion, queries and rollups shared by performance
samples, new benchmarks and reopened benchmark reports, whose raw events are retained for three
years. `CreatePerformanceSamples`, `CreateBenchmark` and `CreateBenchmarkReport` contain the
per-engine settings; sample and benchmark worker counts come from the dashboard, and the benchmark
percentile and index settings and reporting time zone are preserved when reopening a completed
dataset. New sample datasets use the reporting time zone chosen during setup; an existing one keeps the
time zone it was created with. Restart the host to apply edited
sample settings.

## Performance sample data

With the dashboard server in Development mode, open **Tools â†’ Sample data**. Choose an event count (1 to 10,000,000), a date span (1 to 365 days), and parallel workers (1 to 64), then select **Generate sample data**. One worker runs sequentially; higher counts parallelize both sample producers and the sample engine's ingestion workers while retaining visitor event order. Presets include 1,000, 100,000, 1 million and 5 million events. Generation streams events without allocating the full batch. Progress includes submitted and ingested events, elapsed time, live ingestion speed and **Generation throughput**. This average covers event creation, ingestion and flushing, excluding engine preparation. Changing workers preserves the sample store and briefly pauses sample reporting while the engine reopens. The engine's default queue, rollup-buffer and session-cache limits apply per worker. **Cancel generation** stops new submissions, drains accepted events, and keeps them in the dataset.

Select **View sample reports**, or choose **Performance samples** in a report's site selector. These reports use a separate engine and store at `apps/ZoneTree.Analytics.Dashboard/server/data/performance-samples`. Traffic follows the reporting time zone, with quiet nights, busy daytime hours, quieter weekends, growth, campaign spikes and a temporary dip. Visits vary in length, bounce rate and conversions; campaign traffic also changes sources and load times. The dataset includes page views, signups, purchases, bot traffic, device types, sources and geography. Counts describe generated input events; the engine also produces session records. Each generation adds a batch with new visitor IDs. Delete an existing uniformly distributed dataset before generating a fresh one to see the new patterns clearly.

**Delete sample data** closes the sample engine and removes its events, rollups and metadata, then permits a fresh dataset. Primary traffic and its data directory are preserved. Sample controls and endpoints are available only in Development mode, including when `Dashboard:Watch=false`; production hosts do not expose them.

**Benchmark ingestion** prepares the same realistic traffic in memory before timing, then feeds it to a fresh engine with the default per-worker limits. **Include load-time percentile aggregation** controls only percentile rollups; event values and traffic shape are retained. Clear **Maintain dimension and rollup indexes** to measure ingestion without the dashboard's secondary indexes; that run's reports read rollups and raw events directly. **Resolve visitor countries from IP addresses** gives visitors addresses in their countries instead of country dimensions, so the engine looks them up; **Also resolve regions and cities** keeps regions and cities too and needs a database with cities, such as DB-IP Lite. Both are off by default and use the primary engine's IP location files, loaded to the measured precision during preparation. Progress polls lightweight engine counters every 250 ms and shows ingested events, queued events, elapsed time and average throughput so far. The progress bar follows processed events, then shows a separate saving-aggregates stage while the final flush finishes. The result separates preparation, submission, and ingestion-through-flush time. Throughput uses successfully processed events divided by the submission-through-flush interval, with preparation, store creation, dataset publication, disposal and cleanup excluded.

Completed sample generations and benchmarks compact their stores before reporting completion,
moving remaining in-memory records into disk segments and draining their WALs. The dashboard
shows **Preparing reports** during this step. Generation and ingestion throughput exclude this
final compaction step. Cancelled generations retain accepted events without forcing compaction.

Each benchmark uses a fresh GUID directory under `data/ingestion-benchmarks`. The latest successful dataset and its result are retained across restarts; a successful new run replaces the previous one after its report queries finish. Cancelled and failed runs remove their own incomplete dataset and preserve the previous successful run. Select **View benchmark reports** to browse the **Latest benchmark** site over the full generated date range, or select that site in any report. **Delete benchmark data** removes the retained dataset and result. Benchmark reports use `/_analytics/sample-data/benchmark-api`. Primary traffic and generated report samples are preserved. Generation, deletion and benchmarking share a single-operation guard and cancellation. The previous completed benchmark stays visible and browsable during a new run.

Benchmark defaults are **5,000,000 events**, **90 days**, and **20 workers** in both the dashboard and API. For performance measurements, use the same Release build and tiered-compilation setting as the playground. Both projects request server GC; results show the actual build and GC mode. From the repository root in PowerShell, after publishing the dashboard:

```powershell
$env:DOTNET_TieredCompilation = '0'
dotnet run -c Release --project apps/ZoneTree.Analytics.Dashboard/server -- --Dashboard:Watch=false
```

The dashboard server exposes `GET /_analytics/sample-data/status` and JSON `POST` requests to `/generate` (`{"events":1000000,"days":60,"workers":8}`), `/benchmark` (`{"events":5000000,"days":90,"workers":20,"percentiles":false,"indexes":true}`), `/cancel` (`{}`), `/clear` (`{}`), and `/clear-benchmark` (`{}`). Generation workers default to 1; benchmark defaults are described above. Status includes the active operation, generation progress, benchmark preparation/ingestion progress, and the previous completed benchmark result. Its config response advertises both report sites and their endpoints; other sites continue using the configured reporting API.

## Build and host

The dashboard server, performance sample store and ingestion benchmark also enable covering rollup
indexes in both filtering directions for all six pairs among `source`, `country`, `device` and
`page` (12 logical ordered indexes per enabled rollup tier). All logical indexes share one
partitioned ZoneTree store per tier under `rollup-indexes/hour` and `rollup-indexes/day`, giving
two physical stores. The ten-million-row partition target counts combined index copies; the
mutable-segment limit controls when data moves toward disk. Each logical index has its own key
prefix, and values remain full copied rollups. This layout uses a fresh analytics data directory.
Overview cards filtered by any one of these
dimensions read joint aggregates instead of replaying every matching event. The shared explicit
configuration is in `apps/ZoneTree.Analytics.Dashboard/server/DashboardAnalyticsOptions.cs`. On first open after
enabling the combinations, retained raw events backfill the joint rollups; progress is logged.
The main, performance-sample and benchmark engines use host logging. At Information level,
startup logs show timed backfill necessity checks and their reuse/rebuild reasons, followed
by backfill start, progress and completion messages with duration, counts and throughput.
The data directory identifies the dataset; initialization summaries show the total cost.
The host opens retained sample datasets before listening so migrations finish before browser
request timeouts start. Expired raw history cannot be rebuilt. Plan steps keep their rollup tier and expose
the filter's `indexDimension`. Benchmark throughput includes maintaining the new aggregates and
their copied keys and values. To configure other combinations in your own host, use
`Storage.RollupIndexes.Definitions`; the core library leaves the list empty by default.

The dashboard server, performance sample store and ingestion benchmark all enable covering indexes
for `source`, `country`, `device` and `page`. These four logical indexes share one partitioned
store under `indexes/<partition date>`, with separate dimension key prefixes and full copied
event payloads. The default ten-million-row partition target counts combined copies; an event
with all four dimensions contributes four index rows. Mutable segments, WALs, caches,
worker leases and maintenance are shared. Index backfills compact their data to disk before
startup completes. This shared layout uses a fresh data directory.
Existing retained events are indexed when each
store first opens with this configuration; this can add startup time for large datasets, with
progress in the host log. Later clean opens reuse the indexes. Query plans expose indexed reads
as `DimensionIndex` with an `indexDimension`. Benchmark throughput now includes writing these
full-payload copies; the generated event shape is unchanged. Indexes use raw-event retention,
so they accelerate retained data without extending its history. Other applications opt in with
`AnalyticsOptions.Storage.DimensionIndexes.Dimensions`.

```sh
yarn check
yarn build
yarn publish
```

`build` generates `dist/site`; `publish` generates the minified static release in `dist/publish` without uploading it. Serve the release directory with directory-index support, including `/pages/index.html`, `/audience/index.html`, and the other generated routes. No SPA fallback, Node server, external CDN, or browser router is required.

Linting and formatting use the repository's root Biome configuration. From the repository root, run `yarn lint` and `yarn format:check` for checks, or `yarn lint:fix` and `yarn format` to apply fixes. The root `yarn check` includes linting, formatting, and TypeScript checks.

The dashboard loads its settings from `GET /_analytics/api/config` on the dashboard's host. The server builds the response from the stored settings and the signed-in user, listing only the sites that user may read:

```json
{
  "mode": "live",
  "apiBaseUrl": "/_analytics/api",
  "timeZone": "Europe/Berlin",
  "sites": [
    { "id": "shop", "name": "Shop" },
    { "id": "blog", "name": "Blog" }
  ],
  "refreshSeconds": 30,
  "user": { "id": "…", "userName": "olivia", "displayName": "Olivia", "role": "Analyst", "canQuery": true }
}
```

Sites, the refresh interval and the time zone are dashboard settings. Supported refresh intervals are `0`, `30`, `60`, and `300` seconds. A `401` from the config endpoint or the reporting API sends the browser to `/signin/`. For a different reporting API origin, return its URL as `apiBaseUrl` and configure that API's CORS policy to allow the dashboard origin and credentials.

An existing host should register this config endpoint alongside its reporting endpoints, returning only settings the current user can access. The sample registers it on the reporting route group so it shares any authorization policy applied to that group. A missing or failed config endpoint displays a connection error instead of demo reports. No static config asset is published.

For hosting below a path such as `/analytics/`, set PureStack's `basePath` in `content/siteConfig.json` before building, and serve the resulting routes under that path. The config endpoint remains at `/_analytics/api/config`; it is independent of the dashboard's static base path.

| `/events/` | `content/events/events.mdx`, `content/events/events.ts` | Custom events and goal conversion rates |
| `/bots/` | `content/bots/bots.mdx`, `content/bots/bots.ts` | Bot requests and categories |
| `/funnels/` | `content/funnels/funnels.mdx`, `content/funnels/funnels.ts` | Editable ordered funnel steps and conversion window |

| `/account/`, `/account/settings/` | `content/account/` | Profile, signed-in browsers, display name and password |

Each page's MDX and TypeScript live together in its folder. PureStack treats matching folder and file names as folder indexes. The root `index.mdx` imports the shared overview markup so the homepage stays at `/`. Each page component has an exported interface, declarative `html` template, and business logic in the same TypeScript file. `content/components` contains shared typed components with their templates and behavior. `content/lib` contains HTTP contracts, transport, configuration, demo data, and formatting helpers; `session.ts`, `admin.ts` and `settings-model.ts` hold the session, the review-before-save flow and the schema-driven settings form shared by the wizard and the admin pages. `design` holds the PureStack plugin, build-time components, skin, and typed styles.

PureStack provides route generation, header partials, browser entry bundles, icons, the logo and favicon, theme switching, theme palettes, component styles, and static publishing. The plugin selects browser icons from PureStack's catalog at build time and emits a small `assets/dashboard-icons.json`, keeping the full catalog out of page bundles. Regor binds state, conditions, loops, component props, and events. The dashboard uses PureStack's Panel, Btn, Badge, AppForm, FormInputField, FormSelectField, FormStatus, LineChart, and DoughnutChart components. Report values are rendered through text bindings; there is no HTML-string renderer.

Normal page navigation preserves report scope through tab-local sessionStorage. Date ranges, site IDs, comparisons, and filters are also reflected in the URL. Each page owns and cleans up its requests, observers, and refresh timer.

`content/lib/dashboard-model.ts` composes the shared model through exported interfaces for identity, formatting, scope, report data, status, selection, filtering, exports, requests, and lifecycle. The factories in `content/lib/dashboard/` own these responsibilities; filter-dialog behavior stays beside its template in `content/components/report-controls.ts`.

The overview composes small components in `content/overview`: metric cards, the traffic chart, its exact values table, the breakdown grid, top pages, and devices. Each component exports its interface and keeps its template, display calculations, and actions in the same file. Chart components register their PureStack charts locally; the overview entry owns report loading and page composition.

## Reporting behavior

- Requests use the actual camel-case HTTP contract. Rates are fractions; durations are seconds. `null` appears as **â€”**, separately from zero.
- Three reporting requests can run at once, below the API's default concurrency limit of four. Changing scope aborts earlier requests. Network and authentication failures remain explicit.
- Query-plan warnings and incomplete results are displayed. Missing session or bot metrics depend on engine configuration and filters.
- List reports paginate in groups of 20. Their CSV exports contain the displayed rows. The overview exports its time series; queries and funnels export their returned results. CSV text cells are protected against spreadsheet formula injection.
- Funnels need raw-event retention. Bot reports require `BotTraffic.TrackSeparately` and support only compatible filters. Geography needs an IP location database, chosen under **Location** in the settings, or country dimensions on events.
- Device charts use page views, which partition by device. Unique visitors can appear in multiple device groups, so they would not form an additive pie chart.
- Query JSON may override the report controls and exposes the full engine query syntax. Demo queries support a bounded subset; unsupported expressions show an explanation.

## Browser verification

From the repository root, `yarn test:web` runs all TypeScript tests through the shared Vitest configuration: repository scripts, dashboard models, tracker behavior, browser checks, subpath builds, and live tracker ingestion. `yarn vitest` runs the same tests in watch mode.

With Google Chrome installed, build the dashboard and start its .NET host from the repository root:

```sh
yarn workspace zonetree-analytics-dashboard build
yarn dashboard
```

In another terminal, run `yarn test:web`. The live tracker test verifies that dashboard navigation sends accepted beacons and increases the engine's page-view count. Set `ZT_DASHBOARD_TEST_URL` to test a host on a different URL. Normal browser QA keeps automated visits excluded from tracking.

For a smaller run, use Vitest directly: `yarn vitest run --project unit` requires no running host, and `yarn vitest run tests/subpath.ts` selects one file. The browser test starts and stops a local static server, exercises all nine routes, and writes desktop, dark-theme, and mobile screenshots to `test-results`. It also checks API failure and recovery, empty data, pagination, and safe text binding. The subpath test builds a temporary copy under `/analytics/` and checks its generated URLs. Set `ZT_BROWSER_CHANNEL=msedge` to use installed Edge. Setting `ZT_DASHBOARD_TEST_URL` also makes the browser test use that live host instead of its static server.

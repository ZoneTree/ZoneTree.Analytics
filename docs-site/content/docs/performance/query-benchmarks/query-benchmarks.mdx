# 5M-event query benchmark

**Six annual overview reports completed in 33 ms median, with a 5-million-event dataset and previous-period comparisons enabled.** Filtered country and device breakdowns for GitHub traffic returned in about 6 ms median through covering rollup indexes.

These results were collected from the running dashboard on **17 October 2026**. They measure browser/API response time, including response transfer and JSON parsing, in a .NET host.

## Complete overview

Each overview load requests traffic totals, a daily time series, top pages, sources, countries, and devices. Requests run with up to three in flight, matching the dashboard's API client.

| Report scope | All six reports: median | All six reports: p95 |
| --- | ---: | ---: |
| No filter | **33.3 ms** | 35.5 ms |
| source = GitHub | **16.0 ms** | 17.8 ms |
| country = US | **26.5 ms** | 28.7 ms |
| page = /blog | **14.3 ms** | 15.3 ms |

The selected range was **1 January–31 December 2026**, compared with the previous period. Every daily time series returned **365 buckets**. The unfiltered current-period report contained **4,267,778 page views**; the retained dataset also includes earlier traffic and custom events.

Batch time ends when all six JSON responses have been parsed. It includes waiting for a request slot and is measured separately from each request; adding individual medians does not reconstruct the batch time. Chart rendering and initial page assets are outside this measurement.

## What the plans show

The captured plans used **DayRollups** throughout. Filtered multi-dimension reports additionally identified their covering index:

| Filter | Reports using a covering rollup index | IndexDimension |
| --- | --- | --- |
| source = GitHub | Top pages, countries, devices | source |
| country = US | Top pages, sources, devices | country |
| page = /blog | Sources, countries, devices | page |

All 24 report cases returned complete plans with no warnings. All **720 measured requests** succeeded.

These reports answer recurring questions from aggregate state. They do not replay five million individual events on every request. Covering indexes further narrow reads to the matching aggregate keys. This is the mechanism that keeps filtered reports interactive as event history grows.

## Workload and environment

| Setting | Recorded value |
| --- | --- |
| Retained input events | **5,000,000**, all successfully ingested |
| Generated history | 365 days; 17 October 2025–17 October 2026 |
| Fixture | Generated website traffic with visits, sources, geography, devices, custom actions, and load-time values |
| Unfiltered group counts | 6 page paths, 6 sources, 2 countries, 2 device groups |
| Query site / calendar | benchmark-results / UTC |
| Requested range | 2026-01-01 inclusive through 2027-01-01 exclusive |
| Comparison | Previous period: the 2025 calendar year |
| Host | Windows x64, **.NET 10.0.6**, **Release** build |
| CPU | Intel Core Ultra 7 265KF; 20 logical processors |
| Installed memory | 64 GiB |
| Browser | Chrome 155.0.8059.82, headless |
| Transport | HTTP over loopback |
| Numeric load-time percentile aggregation | Off |

The fixture spans parts of two calendar years, rather than a fully populated two-year history. Returned-row limits and the recorded group counts are part of this workload; a report over substantially more groups can require more work.

The host was already running. Storage and operating-system caches were warm; the run did not restart the engine or clear caches. Disk characteristics were not recorded. These are measured results for this workload and environment.

## Measurement procedure

1. Open the dashboard's latest benchmark with `range=this-year`, `tz=UTC`, and `compare=previous-period`.
2. Capture its six reporting URLs and confirm that they address the retained 5M dataset.
3. Run each scope three times to warm it; exclude those loads and the initial navigation.
4. Measure 30 further overview loads per scope, with at most three requests in flight.
5. Time each request from `fetch` through JSON parsing, after it receives a request slot. Use `cache: no-store`.
6. Record batch completion separately, calculate medians and p95, and inspect response plans.
7. Verify that the retained benchmark and sample-operation state did not change during collection.

The result contains **120 measured overview loads** and **720 measured requests**. P95 describes request latency in this measurement; it is independent of the disabled load-time percentile aggregate.

## Recorded ingestion run

The retained dataset also carries the original ingestion measurement. It was not regenerated for these query measurements.

| Measurement | Recorded value | Without indexes |
| --- | ---: | ---: |
| Input / successfully ingested events | 5,000,000 / 5,000,000 | 5,000,000 / 5,000,000 |
| Ingestion workers | 20 | 20 |
| Ingestion throughput | **113,334 events/s** | **260,044 events/s** |
| Ingestion plus final flush | 44.118 s | 19.228 s |
| Submission | 34.678 s | 15.048 s |
| Preparation | 2.432 s | 2.377 s |
| Errors / dropped / rejected | **0 / 0 / 0** | **0 / 0 / 0** |
| Build / GC / tiered compilation | Release / Server / Default | Release / Server / Default |

The recorded run maintains the dashboard's 4 dimension indexes and 12 rollup indexes during ingestion. The run without indexes writes only raw events, sessions, and rollups; it shows the raw ingestion speed, but its filtered reports cannot use covering indexes.

Throughput includes submission, processing, and the final flush. Preparation and the final compaction used to publish the report dataset are excluded. Submission overlaps processing and is already included in the ingestion interval.
